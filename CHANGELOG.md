# Changelog

All notable changes to Tickwright are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

While the version is below 1.0.0, a breaking change raises the minor version (0.1 → 0.2) and anything else raises the patch version. Breaking means any of:

- an API request or response changes in a way existing callers notice;
- an environment variable is renamed or removed;
- a database migration needs a manual step;
- a tracker adapter's `revisionHash` formula changes (it is part of the execution idempotency key).

Prompt files keep their own versions (`src/prompts/execution/*.vN.md`).

## [Unreleased]

### Added

- **Tickwright stops after 3 follow-up rounds on a pull request and hands it back to you.** Once a pull request has had its rounds, new reviews, replies or failed checks no longer start another; Tickwright says so once on the pull request and the ticket. The feedback is kept: raise `maxFollowUpRounds` in the repository's execution policy (0 turns rounds off) and the next check acts on it. A round that fixed a failed check now commits as "Fix the failing check".

- **Tickwright now fixes its pull request when a CI check fails on it.** Once every check on the pull request's latest commit has finished, a check that failed or timed out starts a new round, like a review that requests changes: the agent gets the check's name and the part of its log where it failed, fixes the cause in the code, and asks you to approve the diff before pushing it. A check that was already failing before the agent's change is ignored. As with reviews, this is on only for repositories with someone in `reviewers`. The migration applies on start, with no manual step.

### Changed

- **A failed setup is reported once, not retried, and no longer stops a fix for a failing check.** When a repository's setup command fails, the ticket says so instead of showing a generic failure after three identical attempts. When it fails on the commit a follow-up round starts from (for example, because setup runs the tests and a check failed there), the round sets up on the commit the pull request started from and then works on its own commit, so you change nothing in your repository's setup.
- **A failure note on the ticket now says what happened.** When Tickwright refuses to push (the pull request's branch moved, or the pull request was closed), the note gives that reason. Other failures name the command that shows the details, instead of "Review the execution evidence". Command output is still never quoted, because it can contain secrets.
- **A follow-up round must make a check pass again if it passed when the pull request was opened**, rather than being allowed to leave it failing as an old failure.

- **Tickwright now acts on your feedback on its pull request.** When a listed reviewer submits a GitHub review with "Request changes", or an approver replies on the ticket, after the draft pull request is open, the agent starts a new round on the same branch: it says on the ticket and the pull request what it is working on, changes the code with the feedback in hand (including the lines you commented on), runs the same checks and review as the first change, and asks you to approve the new diff. On `/approve` it pushes one more commit to the same pull request; it never rewrites what is already there. Comments and questions are read as context for the next round but do not start one. One round runs at a time; feedback that arrives meanwhile goes into the next round. The migration applies on start, with no manual step.

- **Tickwright now keeps the feedback you give after its pull request opens.** A reply on the ticket from one of the connection's approvers, and the GitHub reviews and PR comments of someone in the repository's new `reviewers` list (with a review's line comments: file, lines, the code you commented on, and your text), are stored on the execution and shown in `GET /api/executions/:id`. Comments from anyone else and from bots are never read. A review submitted with "Request changes" and a ticket reply are marked as asking for a new change; a "Comment" review or a PR comment is kept as context for that change, so a question never starts work on its own. Nothing acts on the feedback yet: the next release makes the agent address it, with your approval of the new diff before anything is pushed. The migrations apply on start, with no manual step.

### Added

- **Every change is now checked end to end, for free.** Continuous integration takes a ticket all the way to a completed draft pull request (plan, approvals, the agent's work in its sandbox, verification and review) on a real database, message queue and Docker, with a scripted model instead of a paid one. A change that breaks the pipeline is caught before it is merged, not on a paid run. Run it locally with `npm run test:pipeline`.

### Added

- **See what happened to the agent's pull requests.** Tickwright now checks the draft pull requests it opened (every 5 minutes, `PR_POLL_INTERVAL_SECONDS`) and, once one is merged or closed, records it on the execution: merged as written, merged after a person changed it (with the files they changed), or closed without merging. What was merged is kept next to what the agent published, so the two can be compared. The migration applies on start, with no manual step.

### Fixed

- **A tracker connection with missing settings is refused when you create it.** `POST /api/integrations` now answers 400 and names what is missing (for Trello: API key, token, board, label, or a valid repository id), instead of accepting the connection and failing quietly at the next poll. Existing connections are not affected.

### Changed

- **Ready for code hosts other than GitHub.** Everything specific to a code host (its API, the credentials it needs, where git clones from) now lives in one adapter per host, so supporting GitLab or Bitbucket means adding that adapter and nothing else. When you add a repository you can name its host (`provider`) and a connection that holds the host's credentials (`connectionId`), and `POST /api/integrations` checks a code-host connection's settings when you create it. Existing GitHub repositories keep working unchanged (`githubInstallationId` is still accepted). Repositories with the same owner and name on different hosts no longer clash. The migration applies on start, with no manual step. This is the first step toward the agent answering review requests on its own pull requests (roadmap Phase 7).

## [0.2.0] - 2026-11-22

Covers the rest of roadmap Phase 4, which is finished (its gate was met on 2026-11-21): repositories in any language, with their environment found or configured, the agent working with tools by default, a reviewer, and cancel and trace for executions. **Breaking:** `OPENAI_BASE_URL` and `OPENAI_TOOLS_API` are removed, and a set `LLM_PROVIDERS` is now the whole list (see Changed). Migrations apply on start, with no manual step.

### Added

- **The plan covers everything the ticket asks for.** Before planning, the agent lists the requirements the ticket states in its own words. The plan must give an example for each one, or a question when the agent thinks it is wrong or unclear; a requirement it still leaves out is shown to you as a question on the plan. The reviewer then checks the change against every requirement, and one that is missing rejects the change.
- **The agent writes the tests the reviewer asked for.** When the reviewer rejects a change because a case has no test, it now names the code a test for that case must call, and the agent's next attempt cannot finish until its test files call that code (or it says why the case cannot be tested). After two refusals the run goes on, and the reviewer is told what is still missing. New prompt version `reviewer.v9`.

- **Cancel an execution.** `POST /api/executions/:id/cancel` (optional `{ "reason": "..." }`) ends an execution in any state that is not already final: it becomes `CANCELED`, pending approvals are rejected, and an `EXECUTION_CANCELED` event records who canceled it, from which state and why. A run in progress stops at its next step (after the current model call or command), and the environment sweep removes what it left. An execution that has already ended answers 409.
- **The project's own instructions reach the agent.** A repository's `verificationConfig.instructionFiles` lists the files the project keeps for contributors and coding agents (how to name, lay out and test a change). Their text, in that order and within `executionPolicy.maxInstructionChars` (default 20,000 characters), is given to the planner, the agent and the reviewer, which are told it guides how a change is made but never changes what the ticket asks, overrides their rules or permits anything; the reviewer lists a change that does not follow them as a suggestion, not a reason to reject it. Files outside the repository or behind a symbolic link are not read. Nothing is chosen by file name in code: with no files configured, nothing changes. New prompt versions `agent.v7`, `planner.v3`, `reviewer.v7`.
- **See what an execution did.** `npm run trace -- <execution id>` prints one execution as a readable timeline: the plan step, each model reply with the tool calls it made (inputs and outputs in full), commands with their output, edits as removed and added lines, the review, verification and the outcome. `--follow` keeps printing new steps until the execution ends, so a run can be watched live; with no id it lists the executions in progress. It reads the production stack's database through `docker exec` (set `TRACE_DB_CONTAINER` for another stack) and changes nothing. It also prints each model call: the system prompt, the messages new since the previous call, the full reply or the error, and how long it took. The planner's tool calls are stored only as previews, which it labels.
- **Every model call is recorded.** Each try of each model call, failed tries included, is stored with its request (system prompt, messages, tool definitions and reasoning effort, in the app's provider-neutral form, before the provider's request body is built; never the API key or headers), the full reply or the error, and its duration. Records are deleted after `LLM_CALL_RETENTION_DAYS` (default 7; 0 records none); the token ledger is kept as before. From recent token counts, an execution needs about 1.3 MB on average, so a week of heavy eval use is about 1 GB. A failed write is logged and never slows or fails the call. Needs the new migration.
- **Discard a proposed environment.** `PATCH /api/repositories/:id` with `{ "environmentProposal": null }` drops the environment discovery stored for the repository, so the next run discovers one again instead of trying the stored one first. The reference eval uses it whenever a sandbox repository switches to another project, so each project's discovery starts fresh.
- **Flaky checks are run again.** A check that passed on the unmodified code but fails on the change is run once more before it blocks the change. If it passes then, the change goes on, and the change comment and the draft PR say the check failed once and passed on the second run, so the approver can check the change didn't make it intermittent. A check that fails twice still blocks.
- **Untested code is flagged.** The plan comment, the change comment and the pull request say when the repository has no test files, or which of the files to change (or changed) no test names by path or contents, so passing checks are not read as proof. It is a name match, not real coverage. The `PLAN_WRITTEN` event and the diff artifact's metadata record it as `coverage` / `testCoverage`.
- **Test secrets.** `PATCH /api/repositories/:id` accepts `testSecrets` (environment variables for the checks, such as a test-mode API key), stored encrypted. Every check gets them: setup's baseline run, the agent's sandbox and verification. They are never kept in the environment snapshot, are masked in check output, and a change that contains one is rejected. The agent can read them, so they must be test-grade values. Needs the new migration.
- **Limits per repository.** A repository's `executionPolicy` can now set `sandboxCpus` (default 2), `sandboxMemoryMb` (2048), `sandboxMaxProcesses` (256), `checkTimeoutSeconds` (300, for one check or agent command) and `maxFileBytes` (500,000, the largest file the agent may write), and `maxChangedFiles` may go up to 1,000 (before, 100). Unset values keep the earlier fixed limits.
- **Progress of long steps.** While a devcontainer build, setup or a check runs, the execution records a `GRAPH_STEP_PROGRESS` event about once a minute (`EXECUTION_PROGRESS_INTERVAL_SECONDS`) with the step, its command, the elapsed time and the end of its output (secrets masked), so the API shows a run is alive and what it is doing. A step with no new output for `EXECUTION_HUNG_AFTER_SECONDS` (default 600) is marked as possibly hung.
- **Environment sweep.** On start and every hour, the app removes what ended runs left behind (snapshot, containers, network, clone) and repository environment caches and devcontainer builds older than `EXECUTION_SNAPSHOT_MAX_AGE_HOURS` while the repository has no run in progress; only what its own database knows is touched. A run does not start with less than `EXECUTION_MIN_FREE_DISK_GB` (default 10) free after a sweep.
- **Setup secrets.** `PATCH /api/repositories/:id` accepts `setupSecrets` (environment variables such as a private registry token), stored encrypted. Only the setup command gets them; checks, the environment snapshot and the agent never do, and a change that contains one is rejected.
- **Unverified plans are flagged.** The plan comment on the ticket says when nothing will test the change (the repository has no checks) or when checks will only be proposed during the run, and the `PLAN_WRITTEN` event records which applies and the checks that will run.
- **Git submodules.** The clone fetches a repository's submodules at the commit's revisions.
- **Devcontainer builds.** A project whose devcontainer builds a Dockerfile, uses Docker Compose or adds features now runs in the image the official Dev Container CLI builds from it (before setup, with network and without credentials), instead of falling back to the default image. The other Compose services start beside the run as its service containers. Builds that would read files outside the repository are refused and reported.

### Changed

- **Every LLM provider is configured in one place.** `LLM_PROVIDERS` now lists all providers, OpenAI, Gemini and Anthropic included, each with a `type` (`openai-compatible`, `gemini` or `anthropic`). Left unset, nothing changes: you get OpenAI, Gemini and Anthropic as before, with their keys read from `OPENAI_API_KEY`, `GEMINI_API_KEY` and `ANTHROPIC_API_KEY`. **Breaking:** once set, it is the whole list, so an existing `LLM_PROVIDERS` must add any of the three it still uses. `OPENAI_BASE_URL` and `OPENAI_TOOLS_API` are removed; set `baseUrl` and `toolsApi` on the `openai` entry instead.
- **Comments and commits carry the Tickwright name.** Comments on the ticket are signed "— Tickwright" instead of "— Agent Orchestrator" (comments already signed with the old name are still recognised as the app's own, so open cards keep working). The pull request's commit is authored by Tickwright and its message is the ticket's title and the execution id, instead of "fix: automated bug fix" for every kind of ticket.
- **Log unexpected database errors before returning 500.** Prisma known request errors that do not have a specific client response now log their error code and description, while the response stays the same and keeps database details out.
- **The reviewer checks that every case the ticket names is tested.** When a ticket or its plan names more than one case ("and similarly all other operators", several input kinds), or the change makes the same edit in several places, the reviewer now rejects the change unless a test that verification ran reaches each of them, and names the ones without a test so the next attempt can add them. Only cases written in the ticket, the plan or the change count. New prompt version `reviewer.v8`.
- **An environment that cannot build the project is no longer accepted.** Environment discovery used to count a build that fails on the unchanged code as "the project's own errors" and accept the environment, so the project's tests never ran. Since the commit being changed is one the project's CI accepted, discovery now treats such a failure as the wrong compiler or tool version and tries to install the one the project's CI or build files name. New prompt version `discover.v4`.
- **A run with no working environment stops instead of guessing one.** When environment discovery could not prove any environment, the run used to go on in the first one whose checks merely ran, even when those checks were a build that failed on the unchanged code, so the agent worked with no way to test its change. Such a run is now blocked at once with "No working environment was found" and what each attempt tried, before any model work is spent on the change. The message on the ticket now starts with how to fix it once: the exact call that sets the repository's image, setup and checks, or a devcontainer file to add to the project.
- **A run stops when no environment is found.** When a repository has no configured checks and environment discovery cannot get one to work, the run is now blocked right away with "No working environment was found" and a line per attempt (in the execution's error and the ticket comment), instead of going on without checks, where it was usually blocked after about three times the cost of a good run. A run that would have found a fix in the default image without checks is now blocked too; configure the repository's checks and run it again. An environment counts as working once its setup succeeds and every check runs, even if some of the project's tests fail: when discovery cannot confirm the failures are the project's own, it uses the first such environment anyway, counts those checks as already failing, and the change comment and the draft PR say the checks were not confirmed. Discovery also shows the model the end of both the error and the normal output of a failing check (before, a long normal output, such as a coverage table, hid the error), keeps the end of each failure's output in the `GRAPH_ENVIRONMENT_DISCOVERED` event, and no longer re-tries a failed proposal that differs only in its language label. With `EXECUTION_DISCOVERY_MAX_ATTEMPTS=0` runs go on without checks as before.
- **`tool_loop` is the default mode.** With `EXECUTION_AGENT_MODE` unset, the agent now works with the sandbox tools instead of returning whole files in one call (`single_shot`). Set `EXECUTION_AGENT_MODE=single_shot` to keep the old behaviour, for example for an `LLM_PROVIDERS` profile without tool calling, which fails a `tool_loop` run with an error saying so. Deployments that already set the variable are unaffected.
- **The plan is written from the code.** In `tool_loop` mode the plan step now reads the repository with the read-only tools (list, read, search) before it writes the plan, instead of getting the first 20,000 bytes of a few files. Each example now says what the code gives today, worked out from the code, and what it should give after the change ("now 1400; after the change 700"), so a ticket sentence describing the bug is no longer planned as the goal. On the benchmark ticket where half the plans did that, all 10 runs are now correct. Each step is recorded as a `PLAN_STEP` event. A model or reasoning effort configured for `plan` applies to it; `planner` sets one for this mode only.
- **The agent gets 150 model calls per attempt (before, 30).** The count is now only a safety net: a run is ended by its token budget (`EXECUTION_MAX_TOKENS`) and its time limit, which are unchanged, so the most a run can cost is the same. Before, an attempt on a large project could be cut off a few steps from done. Set `AGENT_MAX_STEPS` or a repository's `executionPolicy.maxAgentSteps` to keep a lower number.
- **Retried model calls are logged.** Each time a model call fails and is tried again, the app logs which call it was (model, purpose, execution), which try, how long it took and how long until the next try. Before, a call that hung until its timeout left no trace.
- **`search_code` searches a single file too.** The agent can give a file as the path; before, only a folder was accepted and the call failed.
- **The gson reference project runs in a small image.** Its eval environment now uses the official Maven and JDK 11 image (0.7 GB) instead of the default universal image (15.5 GB), so it fits a 16 GB machine: its environment snapshot is 0.8 GB instead of about 16 GB. The server's default image is unchanged. gson results from now on are not directly comparable with earlier ones.

### Fixed

- **A test's made-up secret no longer blocks the change.** The safety check on the final change took test data such as `secret = "secret
... ERROR forged"` for a real credential and stopped the run. A value counts as a secret only when it is one unbroken token, the way real keys and passwords are written; known key formats and the repository's own secrets are still refused everywhere.
- **Plans no longer come back empty when the model ignores its last-call instruction.** At the end of its planning budget the agent may only submit its plan (or the reviewer its verdict); a model that asked to read more files instead ran out of budget with no plan. Such a call is now refused and the model gets one more chance to submit.
- **A finished ticket is not run again.** Once a ticket's run has opened its pull request, moving the card (for example to Done) or editing it no longer starts a new run with a new plan comment.
- **A sync no longer fails when the tracker poller picks up the same new ticket at the same moment.** `POST /api/integrations/:id/sync` could answer 409 "Unique constraint violation" because both syncs tried to start the ticket's run; it now returns the run the other sync started. The coding eval also cancels the run of a try that failed, so nothing is left waiting at plan approval.
- **A change may edit `package.json` when the repository allows it.** The final safety check refused every change to `package.json`, `package-lock.json`, `pnpm-lock.yaml` and `yarn.lock`, whatever the repository's protected paths said, so in a project whose test script lists each test file a new test could never be registered. Those files are now protected only through the repository's `protectedPaths`, which every change is still checked against; the published draft PR still needs a person's approval.
- **A script the agent makes executable stays executable in the pull request.** The stored, reviewed and published change used to record every file without its execute bit, so a new test script or tool that passed in verification could not run from the pull request. File modes are now kept whenever the workspace's disk can hold them; on a Windows folder mounted into Docker, where every file looks executable, they are still ignored.
- A test that needs the network no longer blocks every correct change. The checks on the unmodified code used to run with network access (setup's), while the agent's sandbox and verification run without, so such a test passed before the change and failed after it, every time. The checks on the unmodified code now run offline too, so the test shows up as already failing, and environment discovery sees the same results verification will. Environment snapshots saved before this change are rebuilt once, because a test tool's cache inside them could still replay the old result.
- The agent can now add its test to a project that lists its tests in a file under the test folder (for example `tests/CMakeLists.txt`). An existing test file may gain lines; the lines it had cannot be changed or removed, and the file cannot be deleted. Before, any change to such a file was refused, so the new test was never built by the project's own checks.
- A broken test command of the agent's own no longer blocks a correct change in verification. The agent cannot finish until the command that runs its new test has passed; if that command can never pass (built outside the project's build, a shell error, a test meant to report failures), the agent is told, runs the test another way, and that command is the one verification runs again. The agent is also told that the command runs on its own in a new container and must build what it needs itself. The reviewer is told when the command was replaced.
- Two runs setting up at the same time no longer lose a freshly saved environment ("No such image: agent-env-…"), which cost a whole setup and could fail the run. Docker image changes (saving, tagging, removing) now happen one at a time within the app.

### Security

- The GitHub token is sent to `https://github.com/` only (before, to any host git contacted during a clone or push), and git may use HTTPS only, so a submodule URL cannot use `file://`, ssh or other transports.

## [0.1.0] - 2026-11-08

First tagged version. It covers roadmap Phases 0–3 and the Phase 4 work done so far.

### Added

- **Ticket to draft pull request.** Trello cards with an eligible label become executions. The agent writes a plan, a person approves it, the agent changes the code in a Docker sandbox, a reviewer checks the diff, a person approves publishing, and a GitHub App opens a draft pull request.
- **Decisions on the ticket.** The agent comments its plan and its change on the card; approvers listed on the connection reply `/approve`, `/reject <reason>` or plan feedback. The same decisions are available through the API.
- **Planning.** The plan step pins the base commit, triages the ticket and writes examples of the expected behaviour and open questions; plans can be revised with feedback.
- **Agent loop with sandbox tools.** The model lists, reads, searches and edits files and runs the repository's checks inside the sandbox, within step, token and output limits, and stops at a finish or a budget.
- **Reviewer.** A separate review step rejects unsafe or unrelated diffs and reruns the agent's tests; only tests that ran count.
- **Any language through the repository's environment.** The sandbox image, setup and checks come from the repository's approved configuration, else its devcontainer, else a universal image, with a discovery step that proposes them for a person to approve once. Tests can run with services such as PostgreSQL.
- **LLM providers as configuration.** Gemini, OpenAI (Chat Completions or Responses API) and Anthropic, plus any OpenAI-compatible endpoint through `LLM_PROVIDERS` profiles. A model and reasoning effort can be set per kind of call, and a daily token limit caps spend.
- **Reliable messaging.** Execution state changes use a transactional outbox and inbox over RabbitMQ, with retry and dead-letter queues.
- **Evaluation.** A coding benchmark with hidden tests across Node, Python, Go and Python with PostgreSQL; a reviewer-only replay; and reference runs on real open-source projects.
- **Security.** Authentication on `/api`, CORS allowlist, rate limiting, encrypted integration and agent credentials redacted from responses, and a production configuration check at boot.
- Apache-2.0 license; GitHub Actions CI running lint, build and unit tests.
- Versioning: this changelog, the version in `GET /health`, and a CI check that a pull request updates the changelog.

### Changed

- The project is renamed from its working name to Tickwright.

### Removed

- The unused agent-to-agent messaging layer and its `Message` table (migration `20261108000000_remove_agent_messages`), an unused work item service, and unused packages (`@google/generative-ai`, `@prisma/extension-accelerate`, `uuid`).

### Fixed

- `POST /api/skills/assign` no longer returns the agent's encrypted API key.
- A failed model listing (`GET /api/llm/models`, `POST /api/llm/discover`) answers 502 `BAD_GATEWAY` with the provider's message instead of a generic 500.
- An MCP resource type without a connector fails with an error instead of returning a simulated success.
